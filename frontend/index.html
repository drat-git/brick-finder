How does it work?

A look under the hood of Rebuilt.

The idea and stack

I built Rebuilt to answer a simple question: what else can I make from the LEGO sets I own? It combines their inventories and compares the pieces with other official sets. The interface uses HTML, CSS, and JavaScript. Python handles inventory processing and matching, SQLite holds the prepared catalog, and Streamlit hosts the interface and connects it to Python.

Preparing the data

A separate import step turns downloaded Rebrickable CSVs into a bundled database. It selects the latest inventory version for each set, expands nested sets and minifigures into individual pieces, and excludes spares. It validates references and checks expanded piece totals against the listed counts; invalid inventories are excluded. Searches use this prepared snapshot, without scraping Rebrickable or needing a live API key.

What happens when you use the controls

  • Search: waits briefly while you type, then queries the catalog for matching names or set numbers.
  • Add / quantity controls: track each physical copy independently, subtract its missing pieces, and add loose parts. Collection changes invalidate previous results.
  • Remove / clear / examples: remove sets, confirm clearing the collection, or replace it with a sample collection after resolving unsaved edits.
  • Find my next build: sends the collection to Python, which aggregates available pieces and compares candidate inventories.
  • Exact / Flexible: match part IDs plus colors, or combine colors for the same part ID. Printed parts and mold variants stay distinct.
  • Buildable now / Almost there: show complete inventories or partial matches. Almost there starts at 80% completion.
  • Filters / sorting / Show more: adjust displayed results using cached matches. Show more adds batches of 18.
  • View build: retrieves missing-piece details and, when applicable, suggested color substitutions.
  • Building instructions: opens LEGO’s official instruction page.
  • Divider: changes the collection panel’s width without affecting matching.

How the matching works

Completion = matched required pieces ÷ total required pieces × 100

Each part contributes the smaller of its available and required quantities. If you have two pieces and a build needs three, that contributes two matches and leaves one missing. Extra copies of another part cannot fill that gap.

The default ranking puts completion first, then fewer missing pieces, then larger builds. A build is complete only when its missing quantity is zero. For flexible-color suggestions, exact colors are reserved first; each remaining piece can be allocated only once within that recommendation.

Design choices and limitations

The hosted frontend communicates through Streamlit’s component bridge. The standalone development preview uses HTTP requests to the same Python service. A private draft lives in your active server session. Optional Firebase email/password accounts save named collections in Firestore. Refreshing requires signing in again; passwords and tokens are never saved in browser storage.

New copies start complete. Missing adjustments reduce each copy independently, and loose parts add extra pieces. Keep assembled protects a copy from the planner while its pieces still contribute to recommendations. Each recommendation is evaluated independently against the same collection, so you may not be able to build several at once. Inventory matching does not verify assembly geometry, and instruction availability varies.

Saving and planning

Save is explicit, with revision checks to prevent overwriting a newer collection. Save as creates new collection and copy IDs. The planner minimizes physical copies dismantled, then color substitutions, using OR-Tools CP-SAT. It checks source capacities and every required quantity. A five-second search may return a complete best plan without proving minimum dismantling. Planning never consumes or reserves pieces.
