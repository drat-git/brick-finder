REBUILT / PRODUCT & ENGINEERING

How Rebuilt works

I built Rebuilt around two questions: what can I make with the LEGO pieces I own, and which sets would I need to take apart?

The interesting work is in the constraints: incomplete sets, duplicate copies, color choices, and builds you want to keep assembled. Here’s how the product and the system handle them.

01 / ARCHITECTURE

One app, with clear boundaries.

I chose a custom HTML, CSS, and JavaScript interface with a Python backend hosted in Streamlit. That keeps matching and optimization in one deployment while giving me control over the product’s layout and interactions.

Public catalog data can be cached across visitors. Private drafts, sign-in tokens, and result caches are isolated per visitor. Bridge requests are queued so Streamlit reruns cannot overwrite an action that is still in flight.

02 / DATA MODEL

Get the inventory right first.

An import pipeline turns Rebrickable CSVs into SQLite. It selects the latest inventory versions, expands nested sets and minifigures into parts, removes spares, and checks references and piece totals. Invalid inventories are excluded. A prepared snapshot makes searches repeatable and avoids live API quotas; adding newer sets requires rebuilding that snapshot.

Each physical copy has its own ID, missing-piece adjustments, and protection setting. Two copies of the same set can be in different conditions. Loose pieces add to the collection separately.

Available pieces = catalog pieces − missing pieces + loose piecesSubtract missing pieces per copy, combine the copies, then add loose stock.

03 / MATCHING

Match quantities, with clear color rules.

Find my next build compares the collection with each candidate’s parts list. For every required part, Python counts the smaller of the available and required quantities. Owning extra wheels cannot make up for a missing window.

Exact colors

Match both part ID and color. This is the default because “ready to build” should mean the pieces match the original design.

Flexible colors

Match the same part across colors. Original-color pieces are allocated first, and each remaining piece can be used only once.

Completion is matched quantity divided by required quantity. Results rank by completion, fewer missing pieces, then build size. Only zero missing pieces earns 100%; rounding can never turn an incomplete inventory into a complete one. Printed parts and different molds keep their own IDs.

04 / OPTIMIZATION

A possible build still needs a practical plan.

Recommendations show what the collection can make. Plan this build answers which physical copies to dismantle. Protected copies are excluded from the plan, and loose pieces can reduce the number of sets needed.

I use OR-Tools CP-SAT, a constraint solver, to minimize copies dismantled first and color substitutions second. The model must fulfill every required quantity without exceeding any source’s capacity. A separate validation step checks the resulting picking list.

The optimization model

Each copy has a yes/no selection variable. Integer variables allocate pieces from selected copies and loose stock to the target. If the target needs N pieces, the cost is (N + 1) × copies + color substitutions. That weighting makes one fewer dismantled copy more valuable than any possible improvement in colors.

A deterministic greedy plan provides a starting solution and a complete fallback. The solver uses a fixed seed, one worker, and a five-second search budget. Model preparation and validation happen outside that search budget.

Product decision: expensive optimization happens after choosing a build. If the search times out, the app can show a validated complete plan, labeled “minimum not proven.” It only claims a minimum when the solver proves it.

05 / PERSISTENCE

Guest first. Save deliberately.

Discovery works without an account. Optional email/password sign-in uses Firebase Auth; Firestore Security Rules restrict saved collections to their owner. App requests carry the user’s ID token, with no privileged Admin SDK in the application.

A save commits the full collection snapshot and its unique name reservation atomically. Revision checks reject stale writes so an older session cannot silently overwrite newer work. This favors consistent collection saves over cloud queries for individual pieces; snapshots are capped at 750 kB.

Private state and tokens stay in server memory. Refreshing ends sign-in, so returning users sign in and load explicitly. If Firebase storage is unavailable, the active draft is preserved and matching continues from the bundled catalog.
